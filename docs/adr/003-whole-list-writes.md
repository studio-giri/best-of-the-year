# Whole-list writes, with `updatedAt` as the concurrency token

Realizes [PRD 002 — List contents](../prd/002-list-contents.prd.md), which owns all user-facing behavior and scope — including *why* a List's Items are committed as one list rather than saved a year at a time. This ADR records only *how* that commit is carried out.

## Decision

A List's Items are written by a single request carrying the **desired end state** of the whole list: `PUT /lists/:id/items` with `{ updatedAt, items: [{ year, name }] }`.

- **Replace, in one transaction.** Years present in the payload are upserted on the existing `unique(listId, year)` index, years absent are deleted, and `lists.updatedAt` is bumped explicitly — Drizzle's `$onUpdate` only fires when that row is itself written, and this write touches `list_items`. The three statements are one transaction.
- **`updatedAt` is also the optimistic-concurrency token.** The payload carries the value the editor read; if the stored one has moved, the save is refused with `409` and nothing is written. Without this, a save built on an older snapshot silently *deletes* Items the payload never mentioned — replace semantics turn a stale write into a revert, not merely a lost edit. The check is what makes concurrent editing from several browsers (which ADR-001 deliberately enables) safe.
- **Authorization is resource-scoped, so it is a service function, not middleware.** `HttpApiMiddleware`/`HttpApiSecurity` model authentication and yield a current-actor service; here there is no actor, only "does this token grant access to *this* list id" — a question that needs the path param. One function beside `mintOwnerToken` resolves the List and its matching token hash in a single query (a left join, so the List row returns whether or not the token matches), failing `ListNotFound` (row absent) or `EditAccessDenied` (row present, no token match). The `Authorization` header is declared on the endpoint spec so the derived client types it on both sides, and declared *optional* there: an absent or non-bearer header is a browser proving nothing, which is `EditAccessDenied`, not a malformed request.
- **Input is normalized on both sides, and the server is the backstop.** Names are trimmed and stripped of C0 control characters; a name that reduces to empty is not an Item and is dropped. The editor normalizes before sending so what it holds already equals what will be stored — which keeps its saved-baseline honest — and the server repeats the work because it cannot trust a client to have done it. A NUL byte in particular survives `String.prototype.trim()`, passes every other check, and is then rejected by Postgres as `22021`; stripping it is what keeps a well-formed request from dying as a defect.
- **The empty-commit floor is counted after normalization, so it too lives in the handler.** PRD-002 REQ-9 refuses a commit that would leave a List holding no games, and unlike the year span that bound *is* static — `minItems(1)` on `items` would express it in the payload schema. It still cannot live there, for a different reason: the schema decodes the payload as sent, and normalization runs after it. A payload carrying one Item named `"   "` is non-empty on the wire and empty once trimmed, so a schema-level floor would pass it and the handler would then write exactly the empty list REQ-9 forbids. The floor therefore counts the Items that survive normalization, beside the year-span check and ahead of the transaction, and refuses the pass whole as `ListWouldBeEmpty` — a `422` carrying nothing to point at, because the commit as a whole is at fault rather than any one year. The check never reads what the List currently holds: an empty payload is refused whether it would empty a full list or re-empty an already-empty one. Judging the payload alone keeps the rule one comparison rather than a state machine, and the only case the distinction would buy — an empty commit against an already-empty List — is one the editor never offers anyway, since nothing has changed (REQ-13).
- **The year span is checked per request, not in the schema.** Static bounds (`maxLength(255)`, one Item per year) live in the payload schema and surface as `400`. The span cannot: a schema is built once at import, so a bound derived from the current year would freeze at whatever year the process started in. So the whole span is checked in the one place that can read a clock — the handler — rather than splitting a static floor from a moving ceiling and giving one year two ways to be refused; both refuse the pass as `YearNotCovered`, a `422` naming the offending year. The server's ceiling is deliberately one year looser than the editor's, because its job is refusing nonsense rather than arbitrating which machine's clock is right. The span's floor and the name ceiling are one shared constant each, read by the column, the contract and the editor, so the same number cannot drift between them; and the span is read on the UTC calendar, so every side agrees which year it is — within hours, where the product tolerates about a week.

## Considered options

- **A write per year (`PATCH` one Item on blur).** Would remove the need for a concurrency token entirely, along with the unsaved-work guard and the draft that survives a reload. Rejected on product grounds recorded in PRD-002.
- **A dedicated integer version column.** Rejected: `updatedAt` is already on the wire, already read by the editor, and already has to be bumped by this write, so a second column would need a migration and buy only immunity to same-millisecond collisions.
- **`If-Match` / `If-Unmodified-Since` instead of a payload field.** Rejected: `If-Unmodified-Since` is second-granularity and would discard the millisecond precision the column already has, and minting opaque entity tags is ceremony for a private API with one generated client.
- **`minItems(1)` on `items` in the payload schema.** Rejected on correctness before taste: the constraint would be evaluated against the payload as sent, ahead of trimming and control-character stripping, so a list of whitespace-only names would satisfy it and still normalize to nothing. It would also surface as an undifferentiated `400` decode failure, where the editor needs a distinct answer in order to say *a list needs at least one entry* — the same reason `YearNotCovered` is a tagged `422` rather than a schema bound.
- **A cap on the number of Items, or on body size.** Rejected as a second lock on the same door: only the years in the Covered Years span are accepted and each may appear once, so any oversized payload necessarily contains a duplicate year and is refused before a row is written.

## Consequences

- `updatedAt` is load-bearing rather than cosmetic. The explicit bump cannot be dropped without breaking conflict detection, and the column's millisecond precision is the granularity of that detection — two saves landing in the same millisecond could both pass. Accepted under ADR-001's low-stakes framing.
- The floor is expressed twice, once per side, and both sides must count the same thing: the editor withholds its commit action on the number of Items the pass *would carry* — normalized, empties dropped — and not on how many fields merely look non-blank. Counting raw field contents would offer the commit for a list of spaces and then have the server refuse it, which is the precise disagreement that normalizing on both sides exists to prevent. Everything the editor reports about a pass reads that same normalized view, so it can never claim unsaved work that a commit would not carry — a claim a person would have no action available to clear.
- A List holding no games stays a state the system stores and serves, reachable by never having committed one and unreachable any other way. The floor removes no case from the public read, which still renders a List with no Items exactly as it did before.
- Validation runs ahead of the transaction, so no partial write is reachable from a well-formed payload. Combined with normalizing NUL bytes away, that leaves no cheap way to force a failure mid-transaction, so the transaction boundary carries no automated test — it is a code-level invariant only.
- The one-query authorization returns the List row, so the caller gets existence, access and the stored `updatedAt` from a single round trip and never needs a second read to tell `404` from `409`.
- The write answers by re-reading the List through the very read the public page uses, so the answer cannot describe the list differently from how a reader will meet it — at the cost of one extra round trip after the transaction commits.
- The write answers with the saved List rather than an empty body, because the editor's next commit needs the `updatedAt` this one produced. With no body the editor's token is stale the moment its first save lands, and a second pass would be refused for having committed rather than for the list having moved — so the response is what lets consecutive passes work without a refetch. That same `updatedAt` is the time the editor reports a commit as having landed, so the field carries two loads at once: the next commit's token, and the only clock the editor trusts for a save it took.
